# Limitations — an honest account

This document exists so nobody, including the team presenting this, ends
up overclaiming on stage. Three tiers:

## Validated against real data

- **Historical dataset model** (`ml/train_historical_model.py`) is trained
  and tested on a real uploaded historical dataset
  (`data/train_delay_data.csv`), with a genuine held-out test split and a
  real MAE printed by the script. This is the one component of the
  project that can honestly be described as "tested against real
  records."

## Working and demoable, but not validated against real-world ground truth

- **Live ETA model** — trained and evaluated entirely on
  `data/train_events.csv`, a *synthetic* dataset generated by
  `data_simulator/simulate.py`. The MAE/quantile-coverage numbers printed
  by `ml/train_model.py` are real measurements, but they're measurements
  against simulated data, not real train movements. Real NTES/CRIS data
  access would be needed to validate this against reality, and that
  access requires institutional cooperation a hackathon team doesn't have
  by default.
- **Anomaly detection** — the Isolation Forest flags statistical outliers
  within the synthetic dataset. It has not been checked against any
  labeled real rare-event dataset (derailments, signal failures, major
  weather disruptions), because no such dataset was available to this
  project. Treat its output as "this looks unusual for this route" rather
  than a calibrated real-world incident detector.
- **SMS/push alerts** — the subscribe → delay → notify pipeline is fully
  functional end-to-end, verified with the stub provider. The real Twilio
  path is implemented (`backend/sms_provider.py`) but requires the
  operator's own Twilio account/credentials to actually send an SMS; it
  has not been exercised against a live Twilio account in this build.
- **Auth/RBAC** — implemented with real JWT issuance/verification and a
  real three-role hierarchy enforced via FastAPI dependencies. This is
  demo-grade, not production-grade: the dev JWT secret has an insecure
  hardcoded fallback if `JWT_SECRET_KEY` isn't set (loudly warned in logs
  when this happens), there's no token refresh/revocation, and the three
  accounts are seeded plaintext-in-code demo credentials, not a real user
  management system.

## Not run in this build — treat any numbers as unverified until you run them yourself

- **LSTM benchmark** (`ml/train_lstm.py`) has not been executed in this
  environment (no heavy `torch`/GPU install available in the assistant's
  sandbox). Run it yourself; its docstring explains the journey-level
  train/test split used to keep the comparison against XGBoost fair. Any
  MAE or latency numbers you haven't personally seen printed by this
  script should not be repeated as fact.
- **Load test** (`scripts/load_test.py`) has not been executed against a
  live server in this environment for the same reason. Run it yourself
  against your own running backend and use those numbers.

## Structurally out of reach for a hackathon team

- **Real NTES/CRIS data feed** — requires an actual data-sharing
  agreement with Indian Railways. No amount of engineering effort
  substitutes for this; it's an institutional access problem, not a
  technical one.
- **Validating the live model's MAE against real historical operational
  data** — same blocker as above: without a real feed (or a
  Railways-provided historical dump with the right granularity), there's
  nothing to validate the live model's error rate against beyond the
  synthetic dataset it was trained and tested on.

## What we'd say to a judge who asks "is this real"

Yes, in the sense that every number in this repo comes from an actual
model trained on actual data and an actual script that actually ran — but
"actual data" for most of this system means the synthetic simulator, not
live railway operations. The one place a real dataset is involved
end-to-end is the historical model. Being upfront about that distinction
is more credible than blurring it.
